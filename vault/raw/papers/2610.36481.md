Abstract.
High-level synthesis (HLS) can schedule only the concurrency made legal by its input description. For feedback-coupled designs, a sequential behavioral model can obscure the architectural state boundaries and hazard resolution needed for efficient overlap. We develop an explicit architectural modeling methodology based on synchronous sequential processes that start in lockstep and synchronize completion before repeating. Persistent state, communication, and feedback control are represented in C++, while HLS schedules and binds operations within that structure. A five-stage RV32I processor illustrates three consequential modeling decisions: which version of a value a consumer reads, when it consumes that value, and how architectural memory actions map to port operations. On a Kintex UltraScale+ FPGA, the CPI-optimized configuration achieves 1.221 cycles per instruction at 220 MHz, compared with 4.000 for an algorithmic HLS baseline and 1.575 at 242 MHz for an Ibex reference. An area-optimized configuration reduces LUTs by 65% and registers by 47%, with 9.7% more benchmark cycles and a 250 MHz achieved clock. These results demonstrate a separation between designer-controlled architecture and tool-controlled scheduling; broader applicability beyond the processor case study remains to be evaluated.

1.
Introduction
High-level synthesis translates sequential source code into parallel hardware through dependence analysis, scheduling, and resource binding. For regular array computations, loop pipelining, unrolling, and task decomposition expose substantial concurrency. Feedback-coupled designs present a different problem: the next computation depends on evolving shared state, and efficient execution requires explicit rules for forwarding, stalls, and redirection. A scheduling directive requests overlap; it does not specify these architectural rules.
A processor makes this distinction concrete. An instruction-set-simulator-style loop fetches, decodes, executes, accesses memory, and commits one instruction. Register indices and branch outcomes are runtime values. Overlapping instructions therefore requires a microarchitecture that handles both value dependencies and control changes. HLS may overlap portions of the behavioral loop, but its legal schedule is constrained by the description’s recurrences and timing. In our baseline, the achieved initiation interval (II) is four; forcing a more aggressive schedule fails the clock target.
The proposed methodology represents the design as synchronous sequential processes over explicitly declared architectural boundaries. Processes start in lockstep, compute concurrently subject to communication dependencies, and synchronize completion before committing selected inter-process state and repeating. The designer specifies the communication and consumption timing that make overlap correct; HLS retains detailed scheduling, internal pipelining, resource sharing, and storage binding subject to those semantics. This is architectural modeling in C++, rather than an expectation that directives will reconstruct an unspecified architecture.
Explicit pipeline-state modeling has precedent, particularly in Comet
(
Rokicki et al., 2019
;
Rokicki et al., 2022
)
. Our contribution is to develop and experimentally examine the modeling choices that determine cost within this formulation. We isolate three choices: registered versus in-flight communication, the stage at which a value is consumed, and the memory operations required by an architectural action. A complete RV32I case study relates these choices to II, achievable frequency, and area, using an algorithmic HLS baseline, an Ibex RTL reference, and CPI- and area-optimized configurations. The general principle applies to describing feedback-coupled concurrency; the experiments establish its effectiveness for this processor family and tool flow, rather than a universal advantage over RTL or other HLS approaches.
2.
Background and Positioning
2.1.
Scheduling, State, and Directives
Loop pipelining overlaps iterations subject to data recurrences, timing, and resource limits. Its II is the interval between iteration starts, not instruction CPI. Dataflow decomposition instead creates communicating tasks, typically with FIFO or channel interfaces. Both mechanisms are useful, but a source-level recurrence must still respect when its state becomes available. True dependencies cannot be removed safely by suppressing dependence checks; false aliasing dependencies may be refined only when independence is established.
The distinction matters for a processor: forwarding sends results backward relative to instruction flow, redirects change the front end, and interlocks selectively hold state. The attempted stream-based formulation reported here makes this concrete. Fetch, decode, execute, memory, and writeback were expressed as free-running
hls::task
processes connected by streams, with the register file and the completion flag remaining shared state. Vitis reports merging decode, writeback, memory, and execute “due to feedback on
regfile
”, then merging all five “due to feedback on
is_finished
”, and extracts a single process function; synthesis then fails because that merged process has non-FIFO I/O. This observation concerns that formulation and tool flow; it does not establish that channel-based designs cannot express feedback.

Its analysis identifies register-file read-after-write and next-PC dependencies in instruction-level behavioral models. Its pipelined formulation declares persistent inter-stage structs, computes temporary stage outputs, and commits them after evaluating stalls. This gives C++ the current-state/next-state discipline familiar from RTL nonblocking assignments. Forwarding selects available results from later-stage registers, and explicit state machines accommodate caches and multi-cycle operations. Comet reports II=1, but Dhrystone CPI=1.9: static scheduling throughput and runtime stall cost are different quantities.
We share Comet’s explicit-state principle and do not claim its invention. Comet establishes that a C++ description can carry persistent inter-stage state under a current-state/next-state discipline; the present study asks what determines performance and area once that structure already exists, and treats the remaining modeling decisions as the object of study rather than as implementation detail. Three such decisions prove consequential, and each changes a measured outcome while leaving the stage structure untouched: which version of a value a consumer reads sets the recurrence delay, when it consumes that value determines which storage bindings are legal, and how an architectural action maps to port operations determines how many accesses must be scheduled. The register file is the clearest example. With branches resolved in decode, the operand read must complete within the same modeled transition, so only a fully partitioned flip-flop register file is legal, and the design pays 601 LUTs and 746 registers for it; moving branch resolution to execute lets the same read cross a stage boundary, after which the identical storage-binding request is accepted as distributed RAM at II=1. The source change is one stage assignment rather than a directive, and no directive alone can produce it. Our fixed-latency evaluation and machine-mode support also differ from Comet’s reported configuration, so its Catapult/Artix-7 results provide context, not a controlled cross-tool or CPI comparison.
The method also invites comparison with RTL design, since both describe behavior in terms of cycles and explicit state. The difference is what the description can be used for. The same C++ that is synthesized is compiled by a standard host compiler, so one source serves both as the executable model used to run programs during development and as the input to synthesis; a change to the hazard rules can be exercised in software before any RTL exists, which shortens the loop between an architectural change and functional evidence about it. The correspondence is not automatic: a modeled iteration equals one hardware cycle only when the schedule reaches II=1 and memory latency is fixed, which is why the hardware cycle counts reported here come from an external counter rather than from the model’s own iteration count. The resulting quality is competitive with a manually developed core of similar configuration: against Ibex, the area-optimized configuration uses 1,980 LUTs against 1,940 and 1,595 registers against 702, and completes the kernel suite in 0.82 times Ibex’s time.

3.
Explicit Architectural Modeling
3.1.

The methodology models a design as a set of synchronous sequential processes. Each process describes a portion of the design through sequential computations, while the processes execute concurrently within a common iteration. In C++, persistent state is declared outside a top-level loop, and process computations are represented within its body. Candidate outputs are kept separate from current inter-process state until the synchronized update. The enclosing iteration represents completion synchronization, realized by the schedule rather than a separate runtime barrier controller.
The designer specifies process boundaries, sequential behavior within each process, communication, and the synchronized update rules. HLS schedules the operations and binds resources subject to those semantics. Architectural state registers and HLS-inserted scheduling registers have different roles: the former define communication between modeled iterations, while the latter realize the computations under timing and resource constraints. A modeled iteration may occupy multiple hardware cycles; II=1 is a measured scheduling outcome, not an assumption of the process model.
3.2.
RISC-V Example: Five Synchronized Processes
The RV32I example assigns fetch (IF), decode (ID), execute (EX), memory (MEM), and writeback (WB) to five synchronous sequential processes. Each performs the work of one pipeline stage. During an iteration, the processes operate on different in-flight instructions, start together, and synchronize before repeating. This concurrent execution across processes is distinct from pipelining successive iterations of an instruction-level behavioral loop.
Persistent state comprises the PC, 32-entry 32-bit register file, machine-mode CSRs, and four valid-tagged inter-process registers. IF/ID holds the instruction and its PC; ID/EX holds the decoded operation, register indices, immediate, operand values, and PC; EX/MEM carries the result or memory address, destination, memory controls, and trap information; MEM/WB carries the result and register-write controls. Valid bits identify instructions and bubbles. Reset empties the pipeline, and
x

0
x0
remains unwritable.
Within each iteration, IF reads instruction memory and forms an IF/ID candidate. ID decodes current IF/ID, reads operands, and forms an ID/EX candidate. EX selects available forwarded operands and computes an EX/MEM candidate. MEM performs the access identified by current EX/MEM and forms a MEM/WB candidate. WB commits the valid oldest result. HLS schedules their concurrency while preserving internal dependencies. The source explicitly defines writeback-to-decode visibility for shared register-file accesses; the current-state/next-state discipline applies to the inter-process registers rather than requiring every side effect to be a pure function.
After all process computations and feedback decisions are complete, the synchronized update selects the next PC and commits, holds, or invalidates the inter-process registers. A hazard-induced hold does not let one process advance to another iteration independently: every process still participates in the common iteration, but its selected architectural state may remain unchanged. 3.3.
Feedback, Hazards, and Communication Timing
For each source operand, forwarding compares its register index with valid later-stage destinations and selects an available matching result instead of the stale decoded value. A load-use dependence cannot use a result before the memory access completes; the interlock holds PC and IF/ID while injecting a bubble into ID/EX, allowing older instructions to advance. Decode-stage branch resolution also requires available operands: the CPI-optimized configuration stalls when a needed operand remains in flight. Taken branches and jumps redirect fetch and invalidate younger wrong-path work. Traps and MRET introduce older redirects from execute; incorrect-path execution and architectural side effects must be suppressed.
Forwarding must prefer the youngest older producer when several in-flight instructions target the same register: selection takes an available EX/MEM result on a valid write match, otherwise a matching MEM/WB result, otherwise the decoded operand, excluding matches to
x
​
0
x0
and treating a load destination as not yet available. The load-use interlock asserts when ID/EX is a valid load whose nonzero destination matches a source the decoded instruction actually uses. Holding the front end retains the dependent instruction while bubbling ID/EX prevents it from executing with unavailable data, and older stages continue until forwarding or register-file visibility satisfies the dependence.
Control feedback requires a corresponding age discipline. A redirect from an older instruction supersedes younger candidate work, while a decode-resolved branch must wait for its own operands. Validity therefore controls not only register propagation but also whether a candidate may write memory, update a CSR, or retire. PC and instruction metadata travel with in-flight work so that a trap records the faulting instruction rather than the current fetch address. These explicit rules are the architectural content that distinguishes the model from simply splitting sequential instruction semantics into five function calls.
The source distinguishes communication through registered stage state from consuming a newly computed in-flight value. A same-transition bypass can shorten the number of modeled transitions to a consumer, but extends a combinational path and potentially a loop-carried recurrence. A registered path breaks that path at the expense of delayed availability. The designer must specify which result is valid at the consumer and how an unavailable result causes a stall; HLS cannot infer a new hazard protocol from a timing directive. Conversely, making these rules explicit does not remove real dependencies or exempt the model from dependence analysis.
The core includes Zicsr, machine-mode handling of environment calls, breakpoints, illegal instructions, and misaligned loads/stores, and the host-target interface used to run tests. The implementation provides both an AXI/DRAM path with instruction buffering and a write-back data cache, and a fixed-latency on-chip memory path. The reported comparative evaluation uses the latter. Variable-latency memory remains a major limitation: the reported external-memory implementation reaches II=169.
The II=169 result is a property of where the variable latency was placed, not of the modeling method. In that implementation the AXI response is awaited inside the modeled iteration, so the memory round trip becomes part of the loop-carried recurrence and the scheduler must size the interval to the worst-case response rather than to the pipeline depth. The model already contains the mechanism needed to avoid this, because a miss is architecturally the same event as a load-use hazard: the consumer cannot proceed, the front end holds, a bubble enters ID/EX, and older work continues. Expressing the memory system as an additional synchronous process with its own persistent state, whose completion is one of the feedback conditions
H
t
H_{t}

This is the same structure Comet uses to accommodate caches and multi-cycle operations. We have not built and measured that configuration, so the external-memory path remains the clearest limitation of the present evaluation.
3.4.
Consumption Timing and Memory Operations
A value’s consumption point determines which storage latency is legal. In the CPI-optimized pipeline, branches consume register operands during decode. A registered register-file read would make those operands arrive too late. The fully partitioned flip-flop implementation supports this timing, at substantial storage and multiplexing cost. Moving branch/jump resolution to execute lets the register-file read cross an explicit stage boundary; the same storage-binding request then becomes compatible with II=1. Two mirrored C++ arrays supply the distributed-RAM reads without hand-written RTL. The architectural price is a later redirect and increased branch penalty, rather than merely a change of storage directive.
Memory operations present a second example. Implementing a byte or halfword store as a word read, merge, and write adds a dependent access. Four independently addressed byte lanes eliminate that read-modify-write in the CPI-optimized design; the area-optimized design instead carries a byte-write strobe with a single-port write. Deferring host-interface acknowledgement also makes two otherwise competing stores mutually exclusive. These changes alter what must be scheduled, rather than asking the scheduler to ignore a real port conflict.
The designer therefore controls stage placement, validity, feedback selection, operand consumption, and memory access semantics. HLS controls the detailed schedule, internal registers, resource sharing, and legal bindings. Exploration alternates between structural changes and scheduling settings, with simulation and hardware measurement checking that the resulting architecture remains correct.

4.2.
Does Explicit Structure Improve the Behavioral Baseline?
The algorithmic baseline implements one instruction per loop iteration without explicit pipeline registers, forwarding, or interlocks. Under a 4 ns target, register-file partitioning improves II from seven to four. The body occupies six scheduling states, so partial iteration overlap exists; this is not a strict absence of HLS pipelining. A forced aggressive schedule produces a 7.34 ns critical path instead of 2.85 ns and fails the target. The measured II=4 is consequently a property of this description and configuration, not a universal lower bound for behavioral HLS.

4.3.
What Remains Necessary to Reach II=1?
Explicit state initially yields II=5, demonstrating that structural concurrency does not guarantee a one-cycle schedule. Deferring host-interface acknowledgement and removing registered boundaries around separately synthesized stage functions reduce II to two. 4.4.
How Do Structural Choices Change Area?
The CPI-optimized model uses 5,604 LUTs and 3,009 registers. Source consolidation replaces six shift expressions with one 33-bit arithmetic-right shifter and bit reversal for left shifts. Eleven adders and seventy-one comparators from separate expressions are consolidated into shared arithmetic/comparison paths; load/store address generation reuses the adder. Computing one CSR write value and enable replaces six write call sites. Together with unused decode removal, counter narrowing, a one-bit trap-target flag in place of a carried 32-bit address, removal of the register-file reset loop, and the single-port byte-strobe memory, these changes yield 2,936 LUTs with unchanged benchmark cycles. The reset loop is restored in the final configuration, where the register file is distributed RAM whose contents are undefined at power-up. Counter narrowing is a feature change and limits equivalence to the tested operating range; it should not be described as preserving all counter behavior.
Holding source fixed while relaxing an 8 ns scheduling target to 10 ns removes 452 registers without changing II or measured cycle behavior, but achieved frequency falls from 246 to 208 MHz. Targets of 6 ns or tighter lose II=1. The clock request therefore controls both scheduling storage and performance.
Moving branch/jump resolution to execute permits the distributed-RAM register file discussed above. In the isolated reported comparison it removes 601 LUTs and 746 registers, adds 40 distributed-RAM LUTs, and removes the fabric read multiplexers. Combined changes yield 1,980 LUTs and 1,595 registers at a 9 ns target; an 8 ns build uses 2,226 and 1,736 and reaches 256 MHz. The reported 65% LUT and 47% register reductions cost 9.7% more kernel cycles and 6.6% more CoreMark cycles. Hardware cycle counts match full-system RTL simulation on the measured kernels.

4.5.
Workload Dependence and Limits
Table
5
shows why the conclusions must remain workload-specific. The CPI-optimized design leads Ibex in CoreMark/MHz (0.971 versus 0.915), but trails it in iterations/s (213.7 versus 221.3), while the area-optimized design reaches 227.8 iterations/s despite a lower normalized score of 0.911. The eight-kernel results and CoreMark consistently motivate reporting area, cycles, and achieved frequency together, but do not cover caches, external-memory stalls, or broader application mixes. Generality is demonstrated conceptually through the state-transition formulation and experimentally on one processor family; non-processor evaluation and a matched RTL architecture remain future work.
5.
Conclusion
Explicit architectural modeling separates the state, communication, and hazard decisions that make concurrency legal from the scheduling and binding decisions HLS can optimize. The RV32I example shows how communication paths, consumption timing, and memory-operation structure determine II and performance–area tradeoffs. The measured configurations demonstrate competitive case-study performance and substantial source-driven area reductions, while differing architectures, memory systems, and tool flows limit broader comparisons. The same steps apply elsewhere: name the persistent state, place the process boundaries, and specify which version of each shared value a consumer reads, when it is consumed, and which ports it requires. The method suits designs whose next state depends on an arbitration or allocation decision: a switch arbiter, a cryptographic round and key schedule, or a cache controller where a miss is a hold condition rather than a longer iteration, none of which we have evaluated here.
